ISSUES FOUND DURING THE FIX (not in the original report)
  - SQLAlchemy 2.1 maps postgresql:// to psycopg v3; the project shipped psycopg2 -> crash on import
  - stale pins (fastapi 0.100) broke the test client; the old tests could not run
  - 422 responses echoed submitted passwords back to the client
  - jobs could be attached to another user's project (IDOR)
  - malformed UUIDs in paths returned 500
  - GET /users/me always failed (UUID vs str schema)
  - app subpackages lacked __init__.py and were dropped from installed builds
  - job detail page crashed for jobs without a result yet
  - program output containing NUL made the result unsaveable in Postgres
  - sandbox had no pid limit, ran as root, had a writable rootfs and unbounded swap
  - a killed worker leaked its in-flight sandbox container (now cleaned up on recovery)
  - HOST_WORKER_TMP=${PWD} mapping did not work on Windows
  - (introduced and caught during final testing) periodic recovery treated the worker's own
    in-flight jobs as orphaned, killing running sandboxes every 60 s. Fixed, regression-tested,
    and verified by an 80-second Java/C++ soak test (18/18 correct).
  - "Run time" included container start-up and compilation, and the 0.5-CPU cap doubled compile
    time: a Java hello world showed ~2 s. Compile and program time are now measured separately
    inside the sandbox (migration 0003), and the default is 1 CPU. Java now shows ~0.6 s compile +
    ~0.1 s run, and submit-to-result is 0.5 s (Python) to 1.2 s (Java).
  - Direct API port bound to IPv4 loopback only: on Windows "localhost" tries ::1 first, adding
    ~2 s to every new connection. Now bound on both 127.0.0.1 and ::1 (UI port was unaffected).
